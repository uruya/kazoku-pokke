# かぞくポッケ：Web・スマホと収益化の方針

調査日: 2026-09-08。対象: `uruya/kazoku-pokke`。料金・制度は調査時点の公式情報。価格案、目標値、工数は本アプリ向けの仮説であり、実績や販売開始の告知ではない。

## 結論

当面は **Webを中心に、ホーム画面から使えるPWAを育てる**。通知のためだけにiOS・Androidアプリを別々に作る必要はない。現在の中核である保育園の提出物・持ち物、家庭のTODO、病院予定、買い物共有はWebで実現できている。

収益化の中心は「記録を保存する」ことより、**毎週の準備と家族への引き継ぎの手間を減らすこと**。家族共有を入口に、繰り返し準備・担当・通知の細かな設定に課金する仮説を検証する。最初から全面有料化すると、家族を招待して価値を感じる前に離脱する懸念がある。

## Webとスマホアプリの比較

| 観点 | Web / PWA | ストア配信アプリ |
| --- | --- | --- |
| ホーム画面 | 対応。iPhoneは追加手順の案内が必要 | ストアからインストール |
| プッシュ通知 | 対応。iPhone/iPadは16.4以降、ホーム画面追加と本人の許可が必要 | OSの通知APIを利用。許可やOS設定の影響は受ける |
| 定時のリマインド | サーバーの定期実行からPush。ブラウザ内のタイマーを閉じた後まで動かす設計は不可 | ローカル通知などを利用しやすい。ただし厳密な到達時刻は保証しない |
| オフライン | 追加実装で可能。端末保存・同期競合・ログアウト時消去の設計が必要 | こちらもローカル保存・同期の実装が必要 |
| ウィジェット・OS連携 | OS機能へのアクセスには制約がある | ウィジェット、App Intents、Watchなどが主価値なら有利 |
| 集客 | URL共有・検索・招待から直接開始 | ストア検索・レビューが入口になるが集客が自動で増えるわけではない |
| 開発・運用 | 現在のコードと公開フローを利用 | OS別の検証、審査、署名、課金管理が追加 |

[WebKitのWeb Push仕様](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)、[Safari 26のホーム画面変更](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)、[MDNのオフライン・バックグラウンド処理](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)。今回追加するのはオンラインで使うPWAの入口で、Pushやオフライン編集は含まない。

ネイティブ化は、継続利用者への聞き取りで「ウィジェットから完了したい」「OS連携がないため使わない」が繰り返し確認され、追加開発費を回収できる段階で再判断する。通知だけが理由なら先にWeb Pushを試す。WebViewで包むだけの案も、審査・課金・OS検証が必要になるため工数ゼロとは扱わない。

## 競合と販売する価値

- TimeTreeは共有カレンダーを入口に、プレミアム月額300円・年額3,000円、添付や表示機能などを提供している。[公式料金](https://timetreeapp.com/intl/ja/premium)
- ぴよログは授乳・睡眠など育児記録と家族共有を提供し、通知や音声入力にも対応している。単なる「育児アプリ」「通知が届く」では差が弱い。[公式配信ページ](https://apps.apple.com/jp/app/id1252857347)、[Appleの紹介](https://apps.apple.com/jp/iphone/story/id1584275683)

かぞくポッケは「保育園に通う0〜3歳家庭の、明日の準備」に絞る。例: 毎週月曜の布団カバー、提出物の期限、誰が準備するかをまとめ、完了したことが家族にわかる。有料候補は①繰り返し持ち物セット、②担当と引き継ぎ、③曜日・時刻を選べる通知。医療判断を生成する機能や写真保管は、現在の強みと原価・運用を踏まえると後順位。

## 料金と採算の仮説

推奨の初回検証案: **1家庭 月額380円（税込）**。家族ごとの追加請求はしない。年額3,800円は継続実績が見えてから検討する。いずれも未確定で、現行利用者への課金は開始しない。

| 無料で残す案 | 有料候補 |
| --- | --- |
| 現行の共有・基本登録・閲覧・メール通知 | 繰り返し準備セット、担当・引き継ぎ、詳細な通知設定 |
| 自分のデータの削除・基本書き出し | 日常の準備を自動化する便利機能 |

Stripe標準カード決済3.6%とBilling従量0.7%を単純合算すると4.3%。380円の手数料差引後は約364円。税、返金、手数料への課税、海外カード等の追加料金、無料利用者の費用、サポート工数は含めない概算。[Payments料金](https://stripe.com/jp/pricing)、[Billing料金](https://stripe.com/jp/billing/pricing)

| 有料家庭数 | 月間売上（380円） | 上記手数料のみ差引後 |
| --- | ---: | ---: |
| 30 | 11,400円 | 約10,910円 |
| 100 | 38,000円 | 約36,366円 |
| 300 | 114,000円 | 約109,098円 |

仮に固定費が月5,000円なら手数料差引後だけで約14家庭、月10,000円なら約28家庭が必要。ただしこれは利益の損益分岐ではない。実際は `固定費 ÷（1家庭あたり税等控除後収入 − 変動費）` を切り上げる。まずRailway・Supabase・Resend・ドメインの実請求と無料家庭分の原価を集計する。

有料100家庭を有料転換率5%で得るには対象の継続利用家庭が約2,000必要。この5%は予測ではなくシナリオ。初期は広告より家族招待、保育園準備に関する検索コンテンツ、利用者への紹介依頼を優先し、獲得経路別の継続率を比較する。ユーザーへの勧誘メッセージはこの作業では送信しない。

ストア課金を一律30%として比較しない。日本のAppleの現行制度にはプログラム・契約継続期間による料率差があり、アプリ外部リンクにも条件付き手数料・報告が発生する。外部決済にすればStripe分だけになるとは限らない。[Apple日本の決済条件](https://developer.apple.com/jp/support/payment-options-on-the-app-store-in-japan/)。Google Playの自動更新サブスクリプションは通常15%と案内されているが、代替課金や対象地域の条件は配信時に再確認する。[Google公式](https://support.google.com/googleplay/android-developer/answer/112622?hl=en)

## 実行順と完了条件

工数は1人での実装・検証の目安で、外部審査や利用検証期間を含まない。

| 優先 | 対応 | 完了条件 / 目安 |
| --- | --- | --- |
| P0 今回 | PWA manifest、192/512アイコン、追加案内と導線 | ビルド・公開URL確認。半日〜1日 |
| P0 公開運用 | OTP・前日メールを別利用者で確認、Cron・送信元・監視・バックアップ復元を確認 | 本番の実行記録を残す。1〜2日 |
| P1 検証 | 5〜10家庭に2〜4週間使ってもらい、忘れ物と準備の手間を聞く | 継続利用理由と有料候補への支払意思を確認 |
| P1 計測 | 作成・招待承認・週次利用・完了の最小イベントを実装 | 家庭単位のファネルと週次コホートが見える。1〜2日 |
| P1 継続価値 | 繰り返し準備テンプレートと担当 | 二重生成・日付・家庭分離・編集が検証済み。3〜5日 |
| P1 通知 | 同意式Web Pushと時刻設定 | iOS/Android実機、取消・失敗・退会時停止を検証。3〜5日 |
| P2 販売準備 | 下記の課金・表示・削除対応 | テスト決済の契約ライフサイクルを確認。5〜10日 |
| P3 ネイティブ | OS連携の需要と回収可能性を再評価 | 具体的な離脱理由と採算が示せること |

計測案: `household_created`、`invite_accepted`、`item_created`、`item_completed`、後に`checkout_started`・`subscription_activated`。本文、子どもの名前、生年月日、メール、病院名、招待トークンを分析イベントに含めない。保持期間・目的を定めポリシーに反映する。既存の最終更新日時だけから継続率を推定しない。

意思決定用の仮目標: 招待承認40%以上、4週目継続30%以上、有料機能を試した家庭の支払意思を複数確認。小標本では率だけで判断せず、分母・利用理由と一緒に記録する。利用継続が弱い段階で課金画面や集客広告だけを増やさない。

## Web Pushを導入するときの設計

1. 個人・端末ごとのPush購読をDB保存し、認証済みユーザーの所有権を検証。VAPID鍵は秘密管理に置く。
2. 利用者が通知設定を押したときだけ許可を求める。拒否・非対応・iPhoneの追加前にはメール通知へ案内。
3. 現在の前日抽出処理を共用し、配信記録はメール/Push/端末ごとに分離。JSTの日付、並行Cron、再試行による重複を扱う。
4. Push先URLを検証し、任意の内部URLに送信させない。期限切れ購読（404/410）を除去し、ログアウト・退会時の解除、共有端末で別アカウントへの通知残存を検証。
5. ロック画面では「確認する予定があります」などを初期値とし、子どもや病院の詳細を送らない。クリック先も再認証・家庭所属を確認。
6. iPhone実機でホーム画面追加、許可、アプリを閉じた状態の受信、取消を検証。通知は到達保証のある医療アラームとして提供しない。

## 課金開始前に必要な対応

- **契約単位**: Householdに対して一つの有効契約。支払者と利用者を分離し、OWNERだけが購入・請求管理を行う。複数家庭の切り替えでも契約が混ざらないこと。
- **決済**: Stripe Checkout + Customer Portal。価格IDはサーバーで許可リスト管理。重複Checkout・多重契約を防ぎ、成功URLへの遷移だけで有料化しない。
- **契約同期**: 署名検証したWebhookを処理し、イベントIDの一意制約・再送・順序逆転・定期照合を設計。支払い失敗、解約予約と期間満了、返金の扱いを決め、権限をサーバーで判定。[Stripeの契約イベント](https://docs.stripe.com/billing/subscriptions/webhooks)
- **解約導線**: 更新日、請求履歴、支払方法変更、解約をアプリから辿れるようにする。課金終了後も既存データを削除せず、基本閲覧・書き出しを保つ。[Customer Portal](https://docs.stripe.com/customer-management)
- **販売条件**: 税込価格、課金周期、自動更新、提供時期、解約方法・期限、返金方針、販売者情報・問い合わせを確定。特商法表示と最終確認画面へ反映。現行の規約ページがあるだけでは販売準備完了ではない。[消費者庁の表示案内](https://www.no-trouble.caa.go.jp/qa/advertising.html)、[最終確認画面ガイド](https://www.no-trouble.caa.go.jp/what/mailorder/guidelines.html)
- **個人情報と運用**: 退会・家庭削除時の他メンバーへの影響を明示。削除依頼の処理、保管期間、データ書き出し、請求記録の保存、漏えい時対応を整備。現在の問い合わせ対応も運用責任者と処理記録が必要。[個人情報保護委員会](https://www.ppc.go.jp/personalinfo/legal/leakAction/)
- **テスト**: 新規購入、認証追加要求、支払失敗、二重クリック、Webhook再送・順序逆転、他家庭からの不正操作、解約予約→満了、返金、復旧後の再照合。Stripeテスト環境を使い、実ユーザーに検証請求しない。

販売者情報・銀行/Stripe本番アカウント・正式価格・返金条件は運営者が決める必要がある。今回はこれらを推測して公開せず、課金を有効にしない。

## 今回の実装と残る確認

実装: `app/manifest.ts`、既存SVGから生成したPNGアイコン、`/install`のブラウザ別案内、対応ブラウザでの追加ボタン、「その他」と紹介ページからの導線。manifestは認証更新処理から除外し、ログイン前にも取得可能にする。

Service Worker、端末への育児データのキャッシュ、Push購読、課金は追加していない。iPhone/Android実機でのホーム画面追加とOTP再ログインは、ブラウザエミュレーションだけで確認済みとは扱わない。変更はDBマイグレーションや環境変数追加なしで既存Railwayフローから公開できる。

検証記録: Node.js 22でLint・型チェック・既存32テスト・本番ビルドに成功。ローカル本番サーバーで390px幅のChromium表示、manifestリンク、PNG寸法、追加イベントの承認・取消・失敗・追加済み状態を確認（イベントは模擬）。実機のOSインストール操作・Push受信は未検証。
